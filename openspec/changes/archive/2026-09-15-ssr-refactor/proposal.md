## Why

The server today hands out static, hand-copied HTML files. Every page repeats the same head, site header, nav, clouds, and footer, and only the profile/embed pages get light placeholder interpolation. As pages grow this duplication invites drift, and the mixed model (static files + regex placeholders) is hard to extend. We want the server to own HTML rendering from reusable templates, and to lay out the codebase so server code and static assets live under a clear `src/` tree.

## What Changes

- Introduce a `src/` folder and move the server source into it: `server.js` and `store.js` become `src/server.js` and `src/store.js`.
- Move static assets under `src/public/` (CSS, client JS, favicon) while keeping the exact same URLs served at the site root (`/style.css`, `/session.js`, etc.), **BREAKING** only for file locations on disk, not for any public URL or client behavior.
- Move HTML page files out of the static assets into EJS templates under `src/views/`, with a shared layout and partials (head, site header/nav, footer, clouds, session script) so page chrome is defined once.
- Serve every page through the server: `/`, `/create`, `/login`, `/search`, `/favorites`, `/embed/:username`, and `/:username` now render server-side via EJS using the shared layout. The static not-found page is replaced by a layout-rendered 404 response.
- Keep dynamic injection identical to today: the profile/embed shell still embeds the inert `application/json` `#buddy-profile` payload, and the 404 page still escapes and shows the requested username.
- Add `ejs` as a dependency (Express renders EJS views server-side).
- Keep all client-side JS byte-for-byte the same: `avatar.js`, `builder.js`, `login.js`, `search.js`, `favorites.js`, `interactions.js`, `profile.js`, `session.js`, `widget.js`, `moods.js` are unchanged and still served as static assets at their current URLs.
- `tests/` imports change to the new `src/` paths; test behavior and coverage are preserved.

## Capabilities

### New Capabilities

- `server-rendering`: The system renders its HTML pages server-side from EJS templates with a shared layout and partials, so site chrome is defined once and pages are complete HTML documents generated by the server.

### Modified Capabilities

- None. Existing page-route, profile-shell, embed, and not-found behavior (site-navigation, user-profile, embed-widget) is preserved; only the implementation moves to server-side templated rendering.

## Impact

- **Code layout**: `server.js`, `store.js` → `src/`; `public/` → `src/public/`; HTML pages → `src/views/` EJS templates.
- **Dependencies**: add `ejs` (^3.1.x) to `package.json`.
- **Server**: `server.js` uses an EJS view engine; static routes and the `express.static` mount now point at `src/public`; page routes render templates.
- **Tests**: `tests/api.test.js` updates imports (`../src/store.js`, `../src/server.js`); all existing assertions stay green.
- **Public surface**: unchanged. URLs, CSP/security headers, inline JSON payload, and 404 escaping behave exactly as before.
